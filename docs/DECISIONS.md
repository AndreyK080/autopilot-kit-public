| D18 | **Программа из нескольких прогонов ведётся оркестратором `/autopilot-program`.** Это чат Claude Code в папке проекта. Он не пишет код, а запускает каждый этап новой сессией (`/autopilot-roles`, затем `/autopilot`), ждёт её, проверяет сдачу детерминированной командой `program.py check` и ведёт `.autopilot/program.json` (источник истины) с видом `.autopilot/PROGRAM.md`. Вопросы будущих этапов задаются пачкой в начале, с рекомендуемым ответом; ответы попадают в бриф каждого этапа. Владельца зовут: вопрос брифинга, провал этапа (гейт, расхождение слепой приёмки, упавший таск), необратимое действие. Решения владельца 23.10.2026: этапы идут в режиме `semi`; сессии этапов — в режиме разрешений оркестратора (`auto`); один прогон на папку; в Codex запуск сессий недоступен — следующий чат владелец открывает сам по команде из файла программы. Пилот — проект R R2: подхватить начатый M1, затем M2 | Сейчас после каждого прогона владелец вручную открывает чат и вставляет команду следующего этапа (D17); Autopilot уже пишет машиночитаемое `state.js`, поэтому итог этапа проверяет код, а не модель |
| D19 | **Поправка к D5: для сессий этапов `kit install` делает копию `~/.claude/skills/autopilot-stage`.** Это оригинальный Autopilot закреплённой версии, у которого во frontmatter другое имя и описание («только для сессий этапов /autopilot-program») и снят `disable-model-invocation`; тело и файлы — без изменений. Оригинал `autopilot` не меняется; копия пересоздаётся при `install`/`update` (маркер `.autopilot-kit-generated`), чужую папку kit не трогает, `uninstall` её удаляет. Только Claude Code. Решение владельца 23.10.2026 | Спайк T10.0: сессия, запущенная из сессии, не может начать прогон — инструмент Skill отказывает навыку с `disable-model-invocation`, а `/autopilot` первой строкой задания приходит обычным текстом |
| D20 | **Обновления Autopilot — через dev-установку и проверку швов; автору не пишем, подстраиваемся сами.** Прод — домашний каталог владельца (закреплённая версия, профиль, навыки, агенты). Dev — песочница `~/.autopilot-kit/trial/home`: полная установка версии-кандидата с копией профиля прода, прод не трогается. `kit check-update` сравнивает файлы `skills/autopilot` на GitHub с lock (сдвиг HEAD из-за других навыков автора — не обновление). `kit trial` ставит кандидата в dev и проверяет швы — всё, на что опираются надстройки: файлы ядра, frontmatter для `autopilot-stage`, настоящий `ap.py` во временном проекте (ожидание, сдача, гейты, `deliverable`), чтение его `state.js` нашими `program.py` и `gate.py`, тексты-якоря (коммит сдачи, режимы). `kit update` не ставит версию с красными швами. Раз в неделю, по понедельникам, задача приложения запускает проверку в новом чате в папке kit и пишет владельцу сводку; в прод ставится только после «да» владельца. Решение владельца 23.10.2026 | Ядро — чужой код без обещаний автора; надстройки зависят от его внутреннего устройства (`state.js`, команды `ap.py`, файлы), и тихая поломка опаснее явного отказа обновиться |
| D21 | **Ход всей программы виден на дашборде программы рядом с чатом оркестратора.** Чат оркестратора — главная точка проекта: он называет себя «Оркестратор · <проект>», все вопросы приходят туда. Страница `.autopilot/program.html` в стиле дашборда прогона Autopilot (те же цвета, карточки, шкала, тёмная тема) читает `program.js` (пишет `program.py`) и `state.js` текущего прогона, сама опрашивает их каждые 5 с: трек этапов, процент программы и этапа, фаза Autopilot, тикеты и тесты, вопрос владельцу, оценка оставшегося времени по средней длительности сданных этапов, решения и допущения, ссылка на дашборд прогона. Отдаёт её локальный сервер, который запускает приложение (`.claude/launch.json` проекта, конфигурация `autopilot-program`), оркестратор открывает её в боковой панели; после каждого события пишет в чат строку трека. Дашборд прогона Autopilot не меняется (D5). Codex — страница в браузере и строка трека. Решение владельца 23.10.2026 | Этапы идут в разных чатах, у каждого свой дашборд; общего хода проекта не видно. Спайк T12.0: панель показывает `file://` только статичным снимком, а страницу с локального сервера — живой |
| D22 | **Лимиты подписки: программа сама встаёт на паузу и сама продолжает после сброса.** Оркестратор читает лимиты приложения (`get_usage`: процент и время сброса 5-часового и недельного окна) перед запуском этапа и при каждом пробуждении. Новый этап не начинается при 5-часовом ≥ 85% или недельном ≥ 90% — пауза до сброса. Во время этапа при 5-часовом ≥ 80% (или недельном ≥ 90%) оркестратор заранее ставит одну разовую задачу приложения «продолжить программу» на время сброса + 2 минуты и обновляет её при следующих проверках. Задача смотрит состояние программы и будит прерванный чат этапа сообщением; если всё идёт — ничего не делает. Пауза видна на дашборде и в строке трека, владелец получает уведомление при паузе и при продолжении. Платное продолжение (extra usage) не включается — только решение владельца. Решение владельца 23.10.2026 | При исчерпании лимита встают все чаты аккаунта, включая оркестратор: ожидать внутри чата нельзя, будить должна задача по расписанию в известное время сброса |
| D23 | **Любая документация на входе приводится к плану программы единого вида; этап сдан, только когда сделано всё, что в него входило.** Документы владельца (свои, из другого чата, принесённые) не меняются: оркестратор пишет из них производный `.autopilot/PROGRAM-PLAN.md` по шаблону `kit/program_plan.md` (ставится рядом с `program.py`, печатается `program.py plan-template`) (цель, ограничения и решения, вопросы владельцу с этапом, этапы: результат, цель, входит / не входит, проверяемые критерии, зависимости, что передаёт дальше, размер, источники). Уровень детализации плана — бриф этапа, а не тикеты: спецификацию и тикеты под исполнителя (Sonnet) пишет внутри прогона сам Autopilot сильной моделью; от плана нужны однозначные рамки, критерии и ссылки на детальные документы. Размер этапа — не больше одного прогона (до T3: ~36 тыс. строк, 12 тикетов; лучше T1–T2). Если документов мало или они не той нарезки — первый этап `P0` (прогон «только документы») пишет план; если нарезка есть — оркестратор дописывает пробелы сам и показывает владельцу. `program.py plan-check` проверяет план детерминированно, `plan-load` загружает этапы и вопросы в программу. Требование брифа этапа, отложенное или снятое прогоном, делает сдачу частичной: оркестратор запускает продолжение того же этапа (до трёх частей, дальше — владелец), а не следующий этап. Решение владельца 23.10.2026 | Документы бывают разной детальности и нарезки; прогон, не уместивший этап, сдаётся с отложенным, а проверка считала его сданным целиком |
| D24 | **Codex получает те же возможности, что Claude Code: одно ядро, два привода.** Общее для обоих — `program.py`, `program.json`, план (D23), дашборд (D21), решения по лимитам (D22), проверка сдачи, тексты для владельца. Привод Claude — сессии приложения, уведомления, `SendMessage`, задачи по расписанию. Привод Codex — чат-оркестратор в Codex: этап — фоновый `codex exec` (в папке проекта, `--sandbox workspace-write` с автоматической проверкой запросов), который запускает и проверяет `program.py`; ответ владельца — `codex exec resume <thread_id>`; пробуждение оркестратора — задача в его же чате (thread automation); лимиты — `rate_limits` из файлов сессий Codex; гейт — хук Stop Codex. Владелец в обоих приложениях видит одно: чат оркестратора, вопросы только в нём, дашборд. Кросс-вендорного оркестратора нет (D4). Каждая новая возможность делается для обоих приводов, расхождения — в `docs/PARITY.md`. Сначала спайк в Codex, его запускает владелец (Claude не вызывает Codex). Решение владельца 23.10.2026 | До сих пор оркестратор, паузы по лимитам и дашборд рядом с чатом были только для Claude Code |
| D25 | **Дашборд программы всегда доступен, а вопросы и сдача этапа доходят до оркестратора, даже если он давно не просыпался.** `program.py` сам держит фоновый сервер дашборда на постоянном порту проекта и поднимает его заново при каждой команде `track` / `check` / `status` / `page`; панель открывается по адресу (`preview_start` с `url`), без конфигурации приложения; каждое сообщение оркестратора начинается строкой трека и строкой ссылок на дашборд программы и текущего прогона; слово «дашборд» открывает его снова. Этап, задав вопрос владельцу или сдав этап, сам пишет оркестратору (`send_message`, `session_id: "parent"`) и шлёт владельцу уведомление. В ходе, начатом сообщением, оркестратор пересылает вопросы и записывает итоги, а следующий этап запускает по слову владельца «продолжай». Решение владельца 23.10.2026 | Пилот проект R M2: сервер приложения для дашборда остановился, и вернуть страницу было нечем; после длинной серии пробуждений приложение перестало будить оркестратора, а Autopilot закрыл отметку ожидания в `state.js`, продолжив другие тикеты, — вопрос про Chromium остался только в чате этапа |
| D26 | **После каждой сдачи этапа оркестратор разбирает его остаток, и следующий этап не начинается, пока остаток не разобран.** Остаток — расхождения слепой приёмки, причины провала (если владелец принял этап «как есть»), «осталось после ревью», замечания ревьюеров, отложенные требования, заглушки; `program.py leftovers <ID>` собирает его из вердикта, `next` отказывает до `leftovers <ID> --done --note`.
